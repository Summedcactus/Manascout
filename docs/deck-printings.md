# Exact-printing edits — Stage 4

Each existing `.ds-entry-printing` area has **Change printing**. The shared drawer/mobile sheet offers artwork-first choices, current/preview markers, inline face navigation and real finish choices. Filters and sorting are collapsed by default; filters cover loaded editions. The first 24 matching choices render with lazy images, then Load more reveals another 24 or requests the next source page. Counts distinguish loaded records from remaining catalogue pages. All-language and variation records are requested; records are identified by their Scryfall UUID, never by an invented treatment suffix. Source-provided premium tags (for example, Surge foil) describe the edition; they do not create additional finish options. No prices are required.

`deck-client.printings()` uses the existing paced queue, timeout, cancellation and short cache. Queries pin Oracle ID, platform and `unique:prints`; pagination is restricted to the Scryfall search endpoint and reconstructed with those same parameters. Catalogue records are **untrusted display hints** and cannot change commander verification. Opening, browsing, filtering or cancelling does not edit the deck.

**Use this printing** calls `DeckPrintings.prepare()`, which fetches the exact UUID through the existing client. Its optional `sameOracleAs` preflight rejects mismatched/incomplete gameplay facts before they can displace a trusted commander record. Oracle ID, name, type, front/full rules, mana cost/value, colour identity, keywords and relevant commander facts must agree. Printings/artwork/finishes may differ. The chosen finish must explicitly appear in `availableFinishes`; it never silently falls back during application. Existing construction checks reject illegal, unknown, stale, wrong-platform, non-game, oversized, acorn and unsupported special-card records. Current legality is checked separately from composition.

`deck-model.replacePrinting()` builds a temporary immutable candidate. It preserves quantity/zone, groups a colliding compatible UUID/finish/zone key, and prunes only unused records. When a commander UUID changes, dependent signature assignments and their keys follow the new UUID. The selected preview follows only when it represented the replaced printing/finish. Generation metadata, including Oracle-based commander identity and targets, is retained. Existing duplicate-copy violations remain visible; curation never silently drops cards to make a deck legal.

Commander eligibility remains in the authoritative client: equivalent Oracle facts retain the existing proof and normal expiry; missing proof requires the usual lookup. The selector never grants eligibility itself. Partner/Background pairing and all other legality checks remain unchanged.

The controller commits only a fully prepared candidate for the still-current session/deck. Closing, panel/filter/card/draft changes and cancellation abort work; late jobs cannot apply elsewhere. Stage 3 reconciles the changed entry key, remaps the scroll anchor/focus to the replacement, and retains unrelated cards/images. Stage 2 recomputes roles and Health from accepted records; there is no DOM-role copying or regeneration.

Version-1 saving, autosave, recovery and JSON backup remain in the existing store. Frame and source-provided premium-treatment metadata are optional and backwards compatible. Unavailable saved UUIDs remain intact with verification warnings. A confirmed exact-UUID 404 invalidates that printing’s freshness, while transient failures retain previously verified records until normal expiry; neither deletes deck entries or selects a substitute. Display preferences and transient selector state are not stored as deck data. A customised-printings counter is deferred: default vs manually chosen provenance is not currently tracked reliably.

Stage 5 can reuse `prepare()` and the pure `replacePrinting()` operation for a temporary batch candidate, then run full current validation and commit atomically. It must preserve cancellation/revision checks, original quantities/assignments and exact finish validation. No bulk presets, retailer integration or optimisation are implemented here.

Tests use deterministic catalogue fixtures, real production modules and mocked HTTP/DOM. Native drawer rendering, mobile scrolling, live catalogue pagination and live Scryfall responses still require browser/service smoke testing.
